# 迭代计划与工程规范

目标：把这个扫雷 Demo 做成"能讲清楚工程思路"的作品集项目，而不是一个能跑就完事的小游戏。
原则：每次迭代只加一个主题，且必须有对应的测试或自检。

## 每轮迭代的固定流程（需求先行）

```
需求条目 → 需求规格 → 设计 → 实现 → 测试 → 提交 → 更新追踪矩阵
```

1. **需求**：新功能先写进 [`docs/REQUIREMENTS.md`](REQUIREMENTS.md)，给它编号（F-xx / N-xx）、优先级和**可测试的验收标准**；
   同时确认它不在"明确不做"清单里。
2. **设计**：写清这个需求落在哪一层（规则 / 对局 / 表示），先动 `core.py` 再动 `ui.py`。
3. **实现 + 测试**：规则先写测试再写实现；界面只负责展示与转发。
4. **提交**：一个提交只做一件事，`feat` / `fix` 提交必须带对应测试。
5. **回填追踪矩阵**：在 `REQUIREMENTS.md` 第 7 节补一行"需求 → 实现位置 → 测试"。
   矩阵里 Must 需求右侧为空，说明还没被验证，不允许对外宣称该功能完成。

## 提交规范（Conventional Commits）

```
feat(core): 新增双击和弦逻辑
fix(ui): 修正高 DPI 下窗口模糊
test(core): 补充数字墙展开用例
docs: 更新迭代计划
refactor(game): 抽出计时器为独立类
chore: 升级 pygame 到 2.6.1
```

- 一个提交只做一件事；重构与功能不混提。
- 每个 `feat` / `fix` 提交前必须跑：
  ```bash
  python -m unittest discover -s tests -t . -v
  python main.py --smoke
  ```

## 分支策略（单人项目从简）

```
main        ← 始终可运行、可截图
feat/*      ← 单个功能，自测后合并
fix/*       ← 修 bug
```

## 代码约定

- 类型注解尽量写全（`from __future__ import annotations`），函数短小；
- 规则逻辑只出现在 `core.py`，`ui.py` 里不允许出现 `if 是雷 then ...` 这类判断；
- 魔法数字进 `theme.py` 或 `config/levels.json`，不散落在代码里；
- 对外可见的行为变化，同步更新 README。
